Problem

Prompt instructions duplicated across four files. Changing a rule (e.g. "no emojis") requires editing briefing.ts and afternoon-update.ts in lockstep. chat.ts instructions are a third, independent variant.

Solution

Extract a PromptBuilder module with three methods — chat, briefing, afternoon — that compose shared base instructions with variant-specific overlays. buildMemoryContext already lives in telegram-utils.ts; pull the rest of the string assembly into the same module.

Wins

  • locality: one module owns every instruction string
  • leverage: three call sites, one interface
  • tests hit one interface, not four scattered prompt strings
  • deletion test: deleting the module forces each caller to rebuild instructions from scratch

Unify agent session lifecycle

Strong in-process

Before — three session patterns

chat.ts

sessionCreated flag
manual error branch

remember.ts

create session
try/finally dispose
sessionCreated flag

telegram-utils.ts

create session
AbortSignal wiring
try/finally dispose

After — one deep module

SessionRunner

run({ tools, prompt, signal?, onReply? })

encapsulates: create, timeout, abort, dispose, error branches

Three call sites → one interface

Problem

Three modules independently manage agent session lifecycle — creation, timeout, abort, the sessionCreated error flag, and disposal. Each has subtle differences: chat.ts reuses sessions from an LRU cache; remember.ts disposes immediately; telegram-utils.ts wires AbortSignal. 17 references to lifecycle concerns across 3 files.

Solution

Extract a SessionRunner module that accepts tools, prompt, and optional signal/callback, and encapsulates the full lifecycle. chat.ts session reuse stays as an outer concern (the runner creates fresh sessions; chat.ts caches them).

Wins

  • locality: timeout, abort, and error logic in one place
  • leverage: every agent call site uses the same interface
  • tests: one session-runner test suite replaces duplicated lifecycle assertions across chat/remember/briefing tests
  • deletion test: each caller would need to reimplement ~25 lines of lifecycle boilerplate

Each extension receives its dependencies. The seam is visible. Tests inject fakes.

Problem

Six extension factories accept fastify: FastifyInstance and reach into it for different things — memoryRepository, calendarClient, telegramClient, env vars. The seam between extensions and their dependencies is invisible. Every extension test must construct a full Fastify mock with the right shape.

Solution

Change extension factories to accept concrete dependencies instead of fastify. memory ext takes MemoryRepository, calendar ext takes CalendarClient, etc. The agent plugin becomes the composition root that wires them together.

Wins

  • interface shrinks: each ext declares what it actually needs
  • two adapters: real repo in prod, fake in tests — the seam is real
  • locality: one place (agent/index.ts) owns wiring; extensions own only tool logic
  • tests tighten: inject a stub repository instead of mocking fastify

After — deepened with query object

MemoryRepository

create · findById · query(criteria) · update · delete

query({ recentDays, resolved, tags, entity, category, page, limit })

One method replaces findForContext, findRecent, findResolvedRecent, findByTags, findByEntity, and findAll.

Problem

MemoryRepository exposes 10 methods, but six of them are query variants (findAll, findForContext, findRecent, findResolvedRecent, findByTags, findByEntity). Each adds a method the caller must learn, but the implementation is a thin SQL wrapper. The interface is nearly as wide as the implementation.

Solution

Collapse the six query variants into a single query(criteria) method parameterized by a query object. The criteria object becomes the seam — callers declare what they want, the implementation handles the SQL. This is already partially done (findAll takes a ListMemoriesQuery); extend it to cover all query patterns.

Wins

  • interface: 10 methods → 5 (create, findById, query, update, delete)
  • leverage: one query method serves 6+ call sites
  • locality: query-building logic concentrates in one function
  • deletion test: deleting query() forces callers to write raw SQL

Top recommendation

Collapse prompt instruction sprawl

It's the shallowest module with the most immediate payoff. Six identical instruction lines duplicated between briefing and afternoon-update, plus a third variant in chat.ts. Every tone or instruction change requires multi-file edits — we saw this in dad39f2 where both briefing.ts and afternoon-update.ts were touched simultaneously. Extracting a PromptBuilder module is low-risk, high-leverage, and makes the instruction surface testable for the first time.
